# Circuit Breaker & Fault Tolerance Design

## 1. Circuit Breaker Reference Table (all 7 instances)

Configuration exactly matches the brief's reference table (Case Studies section), implemented via the generic FSM in `diagrams/circuit-breaker-fsm.puml` and `pseudocode/circuit-breaker.py`:

| Circuit Breaker | Protected Service       | Failure Threshold | Reset Timeout | Fallback Behavior                              |
| --------------- | ----------------------- | ----------------- | ------------- | ---------------------------------------------- |
| CB-FRAUD        | Fraud Detection Service | 3 failures / 10s  | 15s           | Allow transaction with manual review flag      |
| CB-NOTIFY       | Notification Service    | 5 failures / 30s  | 60s           | Queue notification for retry; proceed with txn |
| CB-DB-PRIMARY   | Primary Database        | 2 failures / 5s   | 10s           | Route reads to replica; queue writes           |
| CB-DB-REPLICA   | Read Replica            | 5 failures / 10s  | 30s           | Route reads to primary (rate limited)          |
| CB-CACHE        | Redis Cache             | 3 failures / 5s   | 20s           | Bypass cache; query DB directly                |
| CB-EXCHANGE     | Exchange Rate Service   | 3 failures / 10s  | 30s           | Use last known rate with staleness warning     |
| CB-SETTLEMENT   | Settlement Service      | 2 failures / 5s   | 60s           | Queue settlement for next batch cycle          |

Each breaker is an **independent instance** (see the `CIRCUIT_BREAKERS` dict in `pseudocode/circuit-breaker.py`) — this is deliberate and ties directly into bulkhead design below: CB-FRAUD tripping cannot affect CB-DB-PRIMARY's state, because they are genuinely separate objects with separate failure counters, not a shared global breaker keyed by name alone.

## 2. Bulkhead Isolation — Resource Allocation

Per-dependency thread/connection pool limits, sized so that one slow dependency cannot exhaust capacity needed by another (the BN-003 root cause: "thread pool saturation, 40% request timeout rate" from the original bottleneck report — a single shared pool is exactly what caused this):

| Dependency                                 | Pool Type                       | Pool Size (per app instance) | Rationale                                                                                                                                                                                                         |
| ------------------------------------------ | ------------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fraud Detection Service calls              | Dedicated thread pool           | 20 threads                   | Sized against the 15ms SLA — at 12,000 TPS ÷ 12 payment-service instances = 1,000 TPS/instance, and 15ms per call means ~15 concurrent calls in flight at steady state; 20 gives headroom without over-allocating |
| PostgreSQL connection pool (via PgBouncer) | Dedicated DB connection pool    | 40 connections/instance      | Matches the 2,000+ total pooled connections target (docs/00) divided across ~50 total app instances (payment + account + orchestrator services combined)                                                          |
| Redis connection pool                      | Dedicated connection pool       | 30 connections/instance      | Redis handles far higher connection-multiplexing efficiency than PostgreSQL; sized generously since Redis calls are cheap and frequent (idempotency, rate limits, cache)                                          |
| Kafka producer thread pool                 | Dedicated (async, non-blocking) | 8 threads                    | Kafka producers are typically async/non-blocking by design; small dedicated pool for producer callback handling only                                                                                              |
| Notification Service calls                 | Dedicated thread pool           | 10 threads                   | Explicitly non-critical-path (adrs/004) — small pool is acceptable since a full pool here degrades notification latency, never financial correctness                                                              |
| Exchange Rate Service calls                | Dedicated thread pool           | 5 threads                    | Low call volume (only currency-conversion transactions need this)                                                                                                                                                 |

**The core bulkhead property being enforced:** exhausting the Fraud Detection Service's 20-thread pool (e.g., because CB-FRAUD is repeatedly timing out) cannot consume threads that the PostgreSQL connection pool needs — those are structurally separate pools, not separate priorities within one shared pool. This is what actually fixes BN-003, as opposed to just adding a circuit breaker on top of the same shared-pool architecture that caused it.

## 3. Resolving the Fraud Latency Contradiction (ARB Q4)

**The problem, stated precisely (per docs/00 §8, item 1):** the reference performance budget allocates 10-15ms to fraud detection within a 100ms p99 target that has limited slack (the reference budget's own worst-case total is 32-55ms, leaving headroom — but only if fraud stays within its allocated line). If the ML model genuinely requires 25ms, something has to give, and "skip fraud detection" is not acceptable (FR-007 is a SHOULD, not optional — and skipping fraud entirely on a financial system is not a defensible engineering trade-off regardless of its formal priority level).

**Three options evaluated:**

| Option                                                 | Mechanism                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Latency Impact                                                                                                                                                                   | Trade-off                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Feature caching / precomputed velocity features** | Fraud features (transaction velocity, historical patterns) are precomputed and refreshed asynchronously into the Redis feature store (adrs/005, write-behind), rather than computed synchronously per-request                                                                                                                                                                                                                                                                                                                                                           | Removes feature-computation time from the critical path, leaving only feature _lookup_ (Redis GET, ~1ms) + model inference                                                       | Features are slightly stale (seconds-old) rather than perfectly real-time — an accepted, documented risk, not a silent one                                                                                                                                                                                                                            |
| **B. Two-stage risk check (adopted as primary)**       | Stage 1: fast, deterministic rule-based checks (velocity thresholds, blacklist, amount thresholds — from the `fraud_rules` table, docs/05) run synchronously, budgeted at 3-5ms, and catch the majority of both obviously-safe and obviously-fraudulent transactions. Stage 2: ML inference runs only for the residual "uncertain" transactions that Stage 1 doesn't confidently resolve — a meaningfully smaller fraction of total volume, giving the ML stage more effective time budget per transaction it actually needs to evaluate                                | For the majority of transactions, total fraud-check latency is 3-5ms, well under budget. For the minority routed to Stage 2, the model still needs to fit its own allocated time | Requires Stage 1 rules to be well-tuned (too aggressive → most transactions unnecessarily hit the slow path; too lax → fraud risk shifts entirely onto Stage 2)                                                                                                                                                                                       |
| **C. Bounded fallback + async secondary review**       | If Stage 2 ML inference has not returned within a hard deadline (set at the _remaining_ budget after Stage 1 + upstream stages, not a fixed 15ms regardless of context), the transaction proceeds with a `FLAG_REVIEW` marker rather than blocking indefinitely — CB-FRAUD's existing fallback ("allow transaction with manual review flag") is reused here, not reinvented. A mandatory async secondary ML review then runs post-commit, and any transaction it flags as high-risk after the fact is routed to the existing reversal mechanism (FR-005, 30-second SLA) | Guarantees the synchronous path never exceeds its budget, regardless of ML model behavior                                                                                        | A small window of risk exposure exists between "transaction committed" and "async review completes" — mitigated by keeping this window short (async review is high-priority, typically completing within seconds) and by the fact that Stage 1's deterministic rules already caught the highest-confidence fraud cases before ever reaching this path |

**Decision: B + C combined.** Stage 1 (deterministic rules) absorbs the bulk of transaction volume comfortably within budget. Stage 2 (ML) only evaluates the genuinely uncertain minority, and even then is time-boxed with Option C's bounded fallback as the safety net — this reuses the CB-FRAUD circuit breaker's existing fallback semantics rather than introducing a separate mechanism, keeping the design consistent with the rest of the fault-tolerance architecture instead of a one-off special case.

**Direct answer to Q4 ("You can't skip fraud detection. What do you do?"):** Fraud detection is never skipped — every transaction passes through Stage 1's deterministic checks unconditionally. What's bounded is only the _ML_ stage's worst-case latency, and even when it's bounded out, the transaction is flagged for mandatory follow-up review, not silently waved through with no fraud consideration at all.

## 4. Retry Policies

All retryable operations use the exponential-backoff-plus-jitter shape from `pseudocode/circuit-breaker.py`'s `retryable_operation()`, with the **non-negotiable precondition that the operation must be idempotent before it can be wrapped in a retry** (Section 15's principle, enforced via the `has_idempotency_guard()` assertion in the pseudocode — this is a design-time check, not just a comment, precisely because "financial operations must be idempotent before retrying" is a correctness requirement, not a style preference).

| Operation                        | Idempotency guard                                                                                                                        | Max retries                                                                               | Base backoff |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ------------ |
| OCC balance update               | Version-guarded conditional UPDATE (inherently idempotent — re-running with a fresh read either succeeds correctly or correctly rejects) | 3                                                                                         | 20ms         |
| Kafka outbox publish             | Transactional producer + outbox row's own durable existence (docs/07 §4)                                                                 | 3                                                                                         | 20ms         |
| Saga step (via orchestrator)     | Idempotency key (FR-002)                                                                                                                 | Not retried blindly — routed through saga state machine's resume/compensate logic instead | N/A          |
| Downstream service call (non-DB) | Caller-provided idempotency header, checked server-side before processing                                                                | 3                                                                                         | 20ms         |

| ------------------ | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| CE-001             | Kill primary database node                                                                           | System fails over to replica within 30s; in-flight txns retry; no data loss                                                                                                            | Zero committed txn loss; p99 < 5s during failover; recovery < 30s                                                                                                                                                                                                                            | Automated: Patroni self-heals; manual abort restores primary from snapshot if failover itself misbehaves |

| CE-003             | Saturate Redis cache (evictions)                                                                     | Cache miss rate spikes; DB load increases; CB-CACHE may trip                                                                                                                           | DB does not exceed connection limit; p99 < 200ms during degradation                                                                                                                                                                                                                          | Clear injected memory pressure; verify CB-CACHE returns to CLOSED                                        |
| CE-004             | Kill 50% of payment-service pods                                                                     | Remaining pods handle load; auto-scaler provisions replacements                                                                                                                        | Error rate < 5% during recovery; new pods serving within 90 seconds                                                                                                                                                                                                                          | Auto-scaler self-heals; manual pod restart if auto-scaling itself is impaired                            |

CE-006 is the direct, tested validation of the hot-partition mitigation designed in docs/06 — without it, that mitigation would be a claim rather than a tested claim, and the same evidentiary standard applied to the OCC proof (docs/08) and shard simulation (docs/06) should apply here too.
