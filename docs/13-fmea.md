## §2. Independent Recalculation of FM-003 (Direct Answer to ARB Q10)

**The reference table's RPN of 48 (S=6, O=4, D=2) undervalues this failure mode for our specific architecture, and should be revised upward to 96.**

**Severity: revised from 6 to 8.** The reference table's severity score treats this as a generic cache-layer degradation. But our capacity plan (`docs/12`) deliberately sizes the 32 DB shards to run at **75% utilization at burst** (1,125 of 1,500 safe writes/sec/shard) — not with large idle headroom. A cache-miss-driven 3-5x DB load multiplier, applied against a system already running at 75% of safe capacity rather than 30-40%, has meaningfully less room to absorb before crossing into the exact connection-pool-exhaustion failure mode (BN-001) the entire redesign exists to fix. A generic FMEA template can't know this coupling; our own capacity numbers make it visible, and severity should reflect it.

**Detection: revised from 2 to 3.** The reference score assumes a clean, detectable failure signal. In practice, Redis Cluster degradation is frequently _gradual_ (uneven hash-slot rebalancing, one node running hot before it fully fails) rather than a hard down/up transition — this is harder to detect early via a binary health check than a full node crash, and our `redis_memory_utilization` alert threshold (>80%, per A5.6) is a lagging indicator relative to the point where cache-miss cascading actually begins.

**Occurrence: unchanged at 4.** No architecture-specific reason to revise this — general Redis Cluster node failure rates in cloud environments are reasonably well-understood and don't materially differ for our deployment.

**Revised: RPN = 8 × 4 × 3 = 96**, roughly double the reference figure — still below the 200 mandatory-mitigation threshold, but a materially more honest number, and one that traces to a specific, citable architectural fact (docs/12's 75% burst utilization figure) rather than a generic assertion. This is the shape of answer the ARB is testing for with Q10 — not picking a bigger number, but showing _why_ a bigger number is warranted.

**Why FM-016's Detection score is so high (8):** this is the crux of why it's the single highest-RPN item in the table. Every other failure mode here has some observable symptom before real damage occurs (latency spikes, error rates, alert thresholds). A `min.insync.replicas` misconfiguration produces **zero observable symptom** until the exact moment a broker actually fails and the durability gap is exposed — by which point data may already be unrecoverable. This is precisely the kind of silent, high-consequence risk an FMEA exercise is supposed to surface, and precisely why "manipulating scores to make the system look safe" (a practice this report explicitly avoids per its own scoring discipline) would have hidden it.

### CE-007: Validating the min.insync.replicas Misconfiguration Guard (New)

| Field                 | Detail                                                                                                                                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Hypothesis**        | A policy-as-code CI/CD gate blocks any deployment attempting to set `min.insync.replicas < 2` on the primary transaction topic, before it ever reaches a broker                                        |
| **Blast radius**      | Staging environment only — this experiment deliberately never touches production, since it's validating a _preventive_ control, not a live-system failure response                                     |
| **Injection method**  | Submit a deliberately misconfigured topic-config change (`min.insync.replicas=1`) through the same CI/CD pipeline used for real changes, in staging                                                    |
| **Expected behavior** | The OPA/Conftest policy check fails the pipeline before the change is applied; no broker ever runs with the unsafe configuration, even transiently                                                     |
| **Success criteria**  | Pipeline run fails at the policy-check stage, not at a later stage; failure message clearly identifies the specific violated rule (not a generic pipeline failure)                                     |
| **Rollback**          | N/A — nothing is ever applied to a live broker in this experiment; the "rollback" is simply confirming the pipeline's rejected-change state is clean and doesn't leave partial config artifacts behind |

This experiment is structurally different from CE-001 through CE-006 (it tests a _prevention_ mechanism rather than a _live failure response_), which is itself worth noting: not every high-RPN risk is best validated by breaking something in a running system — some are best validated by proving the thing that should never happen, doesn't get the chance to.
